# WorldForge 用户视角审计汇报规范

> 状态：Active  
> 适用范围：全量代码审计、功能审计、产品设计审计、体验审计、安全审计、恢复审计、发布审计、任务复审、PR审查及治理审查。  
> 核心原则：审计可以在内部使用工程方法定位问题，但对作者汇报时必须先说明真实使用场景和实际后果。工程术语只能作为必要的代码定位辅助，不能代替用户可理解的问题结论。

## 1. 审计报告唯一主线

每个问题必须按照以下顺序说明：

```text
用户做了什么
→ 系统会发生什么
→ 用户会损失什么或困惑什么
→ 严重程度
→ 应达到什么正确结果
→ 必要时补充代码定位
```

如果一个发现无法说明“用户实际会遇到什么”，不得直接作为主要问题写进用户审计结论。纯内部可维护性问题只能放到独立的“内部维护项”，不得与用户缺陷混在一起制造严重感。

## 2. 审计必须从用户任务路径进入

全量审计不能只按目录、模块、类或技术层逐个罗列。必须先覆盖作者真实会走的使用路径，再回到代码和设计文档核对实现。

至少覆盖与当前版本相关的真实路径：

- 创建、打开、移动和继续写作作品；
- 输入正文、自动保存、手动保存、关闭和重新打开；
- 切换卷章、页面、作品和写作模式；
- AI生成、取消、继续、建议稿审阅、采用、撤销和冲突处理；
- 灵感胶囊、规划、人物与世界、设定修改及作者确认；
- 搜索、替换、词典、检查和精准跳转；
- 导入、导出、拆章、并章和跨章移动；
- 备份、恢复、回收站、只读保护和异常重启；
- AI连接配置、凭据、网络失败和本地模型；
- 首次启动、日常续写、窗口缩放、高DPI和不同显示尺寸；
- 成品构建、发布、安装与用户拿到的实际程序。

某次审计范围较小时，只覆盖与该任务真实相关的路径，但不得只看修改文件而忽略相邻用户路径。

## 3. 代码、设计与证据必须互相核对

审计不能只看代码，也不能只按设计文档判断“应该没问题”。每个重要结论至少核对以下三类信息中的相关部分：

1. 产品设计：完整产品规格、功能目录、作者语言、界面交互、验收矩阵、当前任务卡和专项设计；
2. 实际实现：应用界面、桌面主程序、本地服务、数据保存、测试和最近变更；
3. 验证事实：自动测试、完整流程测试、真实截图或操作证据、发布检查和已知风险。

发现三者不一致时，报告主体先说明用户会遇到的结果，再在末尾注明设计或代码位置。

## 4. 每个问题的固定写法

每个确认问题统一使用以下字段：

```text
问题：一句话说明用户遇到的具体问题。

用户场景：用户先做了什么，在什么条件下触发。

实际表现：界面、内容、保存结果或操作结果会怎样。

用户影响：用户会丢失什么、得到什么错误结果、被什么状态误导，或为什么无法继续操作。

严重程度：严重 / 高 / 中 / 低。

正确结果：系统应该怎样表现，用户最终应该得到什么。

代码定位：仅在需要定位修复时填写文件名、函数名或相关设计文档；不得用工程术语代替前面的用户说明。
```

推荐问题标题直接写结果，例如：

- “转换一条灵感后，已有作品设定可能被部分清空”；
- “快速切换章节后，当前页可能显示上一章的生成结果”；
- “保存失败后继续切换页面，用户可能误以为内容已经保存”；
- “恢复操作完成后原作品被直接覆盖，用户失去安全退路”。

禁止只写“状态同步异常”“异步竞争问题”“生命周期缺陷”等用户无法判断后果的标题。

## 5. 严重程度只按用户实际后果判断

### 严重

出现以下任一后果：

- 正文、设定、作品文件或备份丢失；
- 已确认内容被静默覆盖、损坏或无法恢复；
- 用户隐私、凭据或作品内容发生安全泄露；
- 核心写作、保存、打开、恢复等能力不可用；
- 操作会造成无法可靠挽回的作品损害。

### 高

出现以下任一后果：

- 容易生成或写入错误内容；
- 切换作品、章节或任务后结果串到错误位置；
- 系统状态与真实结果明显不一致；
- 用户完成操作后得到与预期明显不同的结果；
- 高风险操作缺少必要预览、确认或恢复保障。

### 中

主要表现为：

- 只在特定条件、连续操作或异常路径中发生；
- 功能仍可继续，但体验明显受影响；
- 用户需要重复操作、绕路或重新确认；
- 当前不会直接损坏作品，但存在明确后续隐患。

### 低

主要表现为：

- 文案、提示、显示、布局或操作细节问题；
- 不影响正确数据和主要流程；
- 用户能够理解并继续完成任务。

任务优先级、测试等级、内部风险编号不得直接替代以上严重程度。

## 6. 工程术语使用限制

以下类型的词汇可以用于代码定位、修复说明或开发附录，但禁止直接作为用户审计结论主体：

- 竞态条件；
- 生命周期所有权；
- 作用域不变量；
- 失败关闭；
- 版本比较；
- 原子事务；
- 状态机漂移；
- 请求代次；
- 幂等；
- 写入所有权；
- 边界反转；
- 依赖方向等纯工程表述。

错误示例：

```text
高：SearchPanel存在竞态条件，请求代次与生命周期所有权不一致。
```

正确示例：

```text
高：用户正在搜索时如果同时保存作品词典，当前搜索可能一直停在加载状态，用户只能重新打开页面或重新搜索。
代码定位：search-panel.tsx、project-dictionary.ts
```

技术根因仍应在实际修复时查清，但审计汇报必须先把它翻译成真实用户后果。

## 7. 设计审计也必须使用同一标准

设计文档中的问题不能只写“缺少状态定义”“缺少回滚策略”“边界不完整”。必须说明这种设计缺口落地后会让用户遇到什么。

例如：

```text
问题：设计没有规定“生成期间切换章节”时旧结果如何处理。
用户场景：用户开始生成后立即切到另一章继续写作。
实际表现：如果实现直接沿用当前设计，旧章节结果可能出现在新章节页面，作者难以判断内容属于哪一章。
严重程度：高。
正确结果：生成任务必须始终绑定启动时的作品和章节；切换后旧结果只能回到原章节或明确进入原章节的建议稿。
```

因此，全量项目审计要同时查“设计有没有留下会造成用户错误结果的空白”和“代码有没有违背已经明确的用户结果”。

## 8. 不得把猜测写成已确认问题

审计结果分为：

- 已确认：代码路径、设计冲突、测试或真实操作足以证明；
- 高可信风险：已有完整触发链，但当前缺少最终运行证据；
- 待核实：只有可疑迹象，证据不足。

主问题清单默认只统计“已确认”和对用户影响明确的“高可信风险”。待核实项单独列出，不得用模糊表述扩大问题数量。

如果后来验证发现原判断不成立，应从问题清单移除，不保留为了显得审计有成果。

## 9. 修复建议只描述用户应得到的结果

审计报告中的“应该怎么处理”先定义正确结果，不要求作者理解具体代码方案。

例如：

```text
转换时只修改用户本次确认过的字段，已有设定必须原样保留；如果确认后作品内容已经发生变化，应停止转换并要求用户重新确认。
```

具体使用哪种锁、版本号、事务、请求标识或状态管理方式，由后续实现阶段根据代码根因决定，不能反过来成为审计报告主体。

## 10. 全量审计最终汇报格式

全量代码和项目设计审计统一按以下顺序输出：

```text
一、结论
- 是否存在会影响真实作者使用的问题
- 严重 / 高 / 中 / 低各多少项
- 当前是否适合继续开发、合并或发布

二、问题清单
- 按严重程度排序
- 同一严重程度优先按用户主路径排序
- 每项使用本规范第4节固定字段

三、设计与实现不一致
- 只列会改变用户结果的差异
- 明确以哪个用户结果为正确目标

四、待核实项
- 明确缺什么证据
- 不计入已确认问题数量

五、修复后的用户验收标准
- 用作者实际操作路径说明怎样才算修好
- 不用工程术语代替验收结果

六、必要的代码定位附录
- 文件、函数、测试、设计文档
- 只为实施者定位，不作为主要结论
```

## 11. AI强制自检

任何AI在提交审计报告前必须逐项检查：

1. 每个主要问题是否说明了用户先做什么；
2. 是否写清系统实际会发生什么；
3. 是否写清用户会损失什么、误解什么或为什么不能继续；
4. 严重程度是否按用户后果判断；
5. 修复目标是否描述了用户最终应得到的正确结果；
6. 是否把工程术语放到了结论主体；
7. 是否存在只有技术名词、没有真实用户场景的问题；
8. 是否把尚未验证的猜测写成了已确认问题；
9. 是否同时核对了相关设计、实现和验证证据；
10. 是否遗漏保存、切换、取消、失败、重启、恢复等真实异常路径。

第6或第7项命中时，报告视为不合格，必须改写后才能提交。
