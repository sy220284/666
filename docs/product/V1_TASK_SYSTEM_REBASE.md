# WorldForge V1.0任务体系重排基线

> 状态：Frozen  
> 日期：2026-07-14  
> 增补日期：2026-07-25  
> 依据：作者明确要求根据V6.5全功能依赖重新设计任务卡，并依据已完成代码复核调整后续未完成任务。  
> 适用：仅任务阶段、任务编号、依赖、阶段门和执行顺序。

## 1. 当前任务执行基线

本文件与以下文档共同构成V1.0任务执行基线：

- `docs/tasks/TASK_INDEX.md`
- `docs/roadmap/V1.0_ROADMAP.md`
- `docs/product/V1.0_TRACEABILITY_MATRIX.md`
- `docs/tasks/M0_TASKS.md`至`M8_TASKS.md`

历史版本曾使用M0—M5/M0.5和24/27张任务卡。2026-07-14重排形成M0—M8九阶段、52张任务卡；2026-07-24增补`M5-00 作者工作流与产品体验收口`，形成53张；2026-07-25根据已完成代码与未执行任务的断裂复核，新增`M5-06 真实状态提取与StateProposal接入`，并修订M4-03以后未完成任务的承接边界，当前任务体系为九阶段、54张任务卡。

完整产品原则与功能边界以`WORLDFORGE_V6.5_FULL_SPEC.md`为准；具体范围、功能ID、Schema、IPC、AI、UI和P0验收以完整规格列出的专项唯一真源为准。

## 2. 重排与增补原因

旧任务体系及后续漂移存在：

1. 缺少无AI基础写作产品门。
2. Volume/Chapter晚于Draft编辑器。
3. SceneBeat在模型建立前被结构任务使用。
4. 恢复点晚于拆并章、导入和批量替换。
5. FTS在AI约束包和用户搜索中重复规划。
6. app.sqlite、Core生命周期和测试基建没有独立任务。
7. 人物弧光、网文节奏和双视觉主题容量与验收不清。
8. 用户功能可能到完整UI阶段才第一次可操作。
9. Renderer实际实现偏离冻结的React/Zustand架构，若拖到M7将与完整体验整合形成高风险双重重写。
10. M0—M3完成后，底层能力已可靠但界面仍存在工程术语侵入、操作层级过密、继续写作缺失、设定编辑工程化和高风险操作依赖`prompt/confirm`等体验债务；若直接进入M5会放大AI交互复杂度。
11. M4后续任务仍按空白系统描述，未承接M0-04 TaskProtocol、M0-07 Prompt/ProviderStub和现有Candidate/Recovery/Import基础，存在重复建设风险。
12. 现有Candidate正文块模型无法无损承载T0结构化骨架，且缺少Core层Skeleton禁止Apply硬门。
13. T1绕过T0与现有“至少一个SceneBeat”输入假设冲突。
14. 真实Provider状态提取没有独立任务承接M4运行时与M3-06 StateProposal闭环。
15. 搜索对象与批量替换对象混淆，写作统计无法区分人工输入和AI/导入/恢复等来源。
16. M5-00与M7向导、工作台和模式范围重叠，需要明确“基础骨架→完整向导/整合”的分工。

## 3. 当前九阶段

```text
M0 工程、安全与运行底座
→ M1 基础写作MVP
→ M2 编辑安全与版本核心
→ M3 规划、设定与连续性
→ M4 检索与AI基础设施
→ M5 作者体验、AI生成候选与状态提取
→ M6 校验、搜索与交付
→ M7 完整UI与体验整合
→ M8 发布硬化与验收
```

共54张独立任务卡。

M5阶段先执行`M5-00`，再依次完成结构化Skeleton、三路径T1、改写、融合、候选审阅和`M5-06`真实状态提取。M5-00未Verified前不得新增面向用户的T0/T1入口；M5-06未完成前不得宣称真实Provider状态提取闭环。

## 4. 历史任务冻结与后续承接

- M0—M3、M4-01和M4-02任务卡及证据保持冻结。
- 已完成任务暴露出的兼容扩展和缺口统一写入后续未完成任务卡。
- 不通过改写历史任务目标、非目标、完成条件或证据来伪装后续能力已经完成。
- 追踪矩阵可增加“基础任务→上层使用→最终验收”映射，但不得重新打开已完成任务的历史状态，除非发现其原始验收本身失实并按专项审计流程处理。

## 5. 基础产品门

M1完成时，即使未配置AI，也必须能够：

```text
创建/打开项目
→ 建卷建章
→ 中文写作
→ 自动保存
→ 字数与当前章查找
→ 手动Version与定稿
→ TXT/Markdown导入导出
→ 数据损坏只读与恢复副本
```

M1未Verified前，AI、人物弧光、节奏分析和完整主题骨架不得计入主线完成度。

## 6. 依赖与执行规则

- `ACTIVE_TASK.md`是唯一活动任务控制文件。
- 具体任务依赖必须对应已Verified任务。
- 阶段依赖如`M3`表示M3全部任务Verified。
- 任务只能引用已经建立的上游表、契约、模型和恢复能力。
- 每张用户功能任务必须包含最小可操作UI。
- Planned任务激活时必须补齐`TASK_TEMPLATE.md`规定的执行附件。
- M3-07—M3-10负责在M4前完成Renderer架构迁移；M5-00负责AI生成功能前的现有作者工作流基础收口；M7-01负责完整向导与三条路径；M7-02负责M6功能接入后的统一整合。
- Prompt Registry、TaskProtocol、Candidate采用、ImportPlan协调器、RecoveryService和模式状态源均只能有一套权威实现。
- M4-04必须生产化M0-07资产；M4-05必须复用M0-04 TaskProtocol。
- M5-01必须在Core层禁止Skeleton进入正文；M5-06只创建pending StateProposal。
- `work`分支不受本次规划分支直接覆盖；其代码和任务卡在合并前按新任务体系复核并处理冲突。
