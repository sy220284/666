# WorldForge V1.0 开发路线图

> 状态：Active  
> 基线：WorldForge V6.5  
> 原则：已完成底座保持冻结；V1剩余功能由M4-04统一规划、连续实施和整体关闭。

## 1. 总体顺序

```text
M0 工程、安全与运行底座（Verified）
→ M1 基础写作MVP（Verified）
→ M2 编辑安全与版本核心（Verified）
→ M3 规划、设定、连续性与Renderer架构（Verified）
→ M4-01 FTS（Verified）
→ M4-02 约束包（Verified）
→ M4-03 Provider（Verified）
→ M4-04 V1剩余功能整体实施与发布闭环（In Progress）
→ V1.0发布判断
→ 真实作者使用与长篇数据收集
→ V1.5单独立项
```

原M4-05—M8-03继续作为M4-04的详细需求来源和内部实施范围，不再作为独立路线节点。

## 2. 为什么整体收口

当前代码已经形成完整基础产品、编辑安全、连续性、FTS、约束包和Provider底座。继续逐张推进会把同一用户功能拆散到Schema、Core、IPC、UI和后置验收中，增加合同返工、重复真源和代码断裂风险。

整体收口后：

1. 先读取全部剩余要求、权威文档和全量代码。
2. 统一冻结共享合同、Migration顺序、IPC入口、用户路径和测试矩阵。
3. 每项功能按Contracts→Core→Main→Preload→Renderer→测试形成纵向闭环。
4. 内部阶段只用于排序和复查，不切换活动任务。
5. 一个长期Draft PR承载全部实现，最终只形成一个Ready Head和一次受控合并。

## 4. M4-04内部阶段

### 阶段一：全量基线审计与整体规划

- 读取原M4-04—M8-03全部要求。
- 审计Contracts、Domain、Migration、Repository、Core、Main、Preload、Renderer和测试。
- 建立需求—代码—用户路径—测试—P0映射。
- 冻结共享合同、Migration、IPC、错误码、失败传播和回滚策略。

未完成整体规划不得开始新增功能代码。

### 阶段二：AI公共合同与运行底座

- 生产化Prompt Registry、Parser、Cleaner和Eval。
- 建立T1三种互斥来源、state_extract合同、GenerationRun和GenerationResultRef。
- 建立Skeleton/Prose判别模型、partial和真实重启语义。
- 复用TaskProtocol，不建立第二套AI运行时。

### 阶段三：作者体验与AI写作闭环

- 作者语言、继续写作、正文中心、设定表单和结构操作可视化。
- T0、T1、快速/结构改写、Beat/Segment融合、候选审阅、安全采用和撤销。
- 所有AI正文结果先持久化为Candidate。

### 阶段四：状态提取、校验与连续性

- Final Version→state_extract→StateProposalBatch→pending提案→作者裁决。
- ValidationIssue、稳定锚点、待办与批注。
- 确定性、基础统计、AI语义、知情、伏笔和人物弧光校验。

### 阶段五：搜索、统计、导入与恢复

- Draft/Version/Entity搜索与安全ReplacePlan。
- mutationOrigin、人工写作会话和建议级网文节奏指标。
- DOCX安全导入、多格式Version导出。
- 日常滚动、重大恢复点、命名快照、配额清理和恢复新副本。

### 阶段六：完整体验、硬化与发布关闭

- 首次向导、三条创作路径、全工作台和StatusArbiter。
- Theme A/B、键盘、焦点、读屏、响应式和DPI。
- 安全、Migration、隐私、性能、Electron E2E、AI Eval和三平台构建。
- P0追踪关闭、文档同步和发布判断。

## 5. 关键硬门

### 数据与作者裁决

- 所有正文写入继续经过Patch、Revision、Hash与LockGuard。
- Skeleton进入正文Preview、Diff、Apply、Version或定稿次数为0。
- partial不得默认整稿采用或直接定稿。
- state_extract只创建pending StateProposal，AI不得直接写权威状态。
- pending/rejected/旧Version提案不得作为权威事实。

### 共享真源

- Prompt、TaskProtocol、Candidate采用、ImportPlan、RecoveryService、模式和主题状态各只有一套实现。
- UI不得成为正文、Candidate、状态、任务、搜索或恢复的权威来源。

### 产品完整性

- 无AI时创建项目、写作、保存、Version、导出和恢复完整可用。
- 每个功能从正式入口可操作，并覆盖失败、取消、冲突、只读、恢复和重启。
- 未完成能力不可见或明确禁用。

### 发布

- P0-001—P0-075全部Verified或明确Blocked。
- 安全、Migration、恢复、性能、E2E、Eval和显示矩阵有真实证据。
- Windows、macOS、Linux有真实构建验证或可审计Blocked结论。
- README和用户文档只描述真实可用能力。

## 6. 分支与合并

```text
正式分支：work/m4-04-v1-integrated-delivery
正式PR：一个长期Draft PR
内部交付：可定位原子提交组
转Ready：全部V1功能、测试、文档和证据完成后
合并：六项永久门禁通过后一次受控合并
关闭：M4-04一次整体Verified，且不自动激活下一任务
```

## 7. V1.5启动门

V1.5不得按日期自动开始，必须满足：

1. V1.0已经完成真实发布判断并稳定使用。
2. 已有中型或长篇项目数据。
3. FTS召回、失效传播或自动日记需求有可重复证据。
4. Core性能仍有余量或达到明确拆分阈值。

V1.5继续独立立项，不混入M4-04。
