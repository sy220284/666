# WorldForge V1.0 开发路线图

> 状态：Frozen  
> 基线：WorldForge V6.5  
> 原则：先安全运行，再交付无AI基础写作产品；高级能力只能建立在已验证基础上。

## 1. 总体顺序

```text
M0 工程、安全与运行底座
→ M1 基础写作MVP
→ M2 编辑安全与版本核心
→ M3 规划、设定、连续性与Renderer架构收口
→ M4 检索与AI基础设施
→ M5 作者体验、AI生成候选与状态提取
→ M6 校验、搜索与交付
→ M7 完整UI与体验整合
→ M8 发布硬化与验收
→ V1.0
→ 真实作者使用与长篇数据收集
→ V1.5单独立项
```

## 2. 为什么重排

旧路线在M1之前没有明确的基础可用产品门，且存在章节模型、恢复点、FTS和SceneBeat等依赖倒置。当前路线进一步根据已完成代码复核修正后续承接关系：

1. M1明确交付无AI也能长期写作的基础产品。
2. Volume/Chapter、app.sqlite、Core生命周期和恢复点前置。
3. FTS、Candidate、备份和Prompt拆为公共底座与上层使用，避免重复实现。
4. 每个功能任务同时接通最小UI，M7只做向导、全功能整合和终验。
5. M5在AI生成界面接入前先完成作者语言、继续写作、工作台层级和高风险操作体验收口。
6. M4-04生产化M0-07 Prompt Spike，M4-05复用M0-04 TaskProtocol，不建立第二套运行基础。
7. M5-01扩展结构化Skeleton Candidate并建立Core禁止Apply硬门。
8. M5-02支持Skeleton、SceneBeat和直接章节目标三条T1路径。
9. M5-06补齐真实Provider状态提取与StateProposal作者裁决接线。
10. M6明确搜索/替换对象边界，并区分人工写作与AI、导入、恢复等变更来源。
11. M7复用M5-00基础骨架，避免再次重做模式、导航、三栏布局和沉浸状态。
12. 已完成任务卡保持冻结，新增缺口由未完成任务承接。

## 4. 关键阶段门

### M0退出门

- 干净环境可安装、lint、typecheck、test、build。
- Electron安全壳、Core监管、SQLite、IPC和测试基建可运行。
- 显示/DPI、AI输出模式和中文Diff有量化决策。

### M1基础产品门

作者必须能够在不配置AI的情况下：

```text
创建/打开项目
→ 建卷建章
→ 中文写作
→ 自动保存
→ 字数与当前章查找
→ 手动版本与定稿
→ TXT/Markdown导入导出
→ 数据损坏只读与恢复副本
```

M1未Verified前，不得把后期AI、人物弧光、节奏检测或主题代码计为主线完成度。

### M2数据安全门

- 所有正文写入统一经过Block Patch、Revision、Hash与LockGuard。
- Candidate隔离、冲突、采用和撤销在Fixture场景中先验证。
- 拆章、并章和永久删除均有恢复点。

### M3权威连续性门

- 规划不自动修改正文。
- AI或规则产生的状态变化只进入StateProposal。
- pending提案不改变EntityState或ArcMilestone。
- Renderer完成React、Zustand UI边界、Bridge适配、统一状态与Design Token迁移。
- 旧命令式DOM入口退役，M4不得继续向旧`index.ts`堆入业务功能。

### M4 AI基础门

- FTS和约束包可追溯。
- Provider凭据不进入数据库和Renderer；不安全`safeStorage`后端必须阻断。
- M4-04生产化现有Prompt Spike，不存在第二套Registry、Cleaner或Parser。
- M4-05复用TaskProtocol，GenerationRun、Candidate、Prompt和约束引用完整。
- 取消后无未来delta进入Renderer，重启不伪装网络流已恢复。
- AI不可用不影响M1—M3。

### M5作者体验与可控AI门

- M5-00先完成作者语言层、继续写作、正文视觉中心、设定作者化、高风险操作可视化和模式状态统一。
- M5-00未Verified前，不得激活M5-01或新增面向用户的AI生成入口。
- Skeleton结构化内容可持久化、编辑和追溯，进入正文Apply或Version的成功次数为0。
- T0可绕过，T1支持Skeleton、权威SceneBeat和直接章节目标三条路径。
- 所有AI正文输出始终先成为Prose Candidate。
- partial不得默认整稿采用或直接定稿。
- Final Version→state_extract→pending StateProposal→作者裁决闭环可用，AI不直接写权威状态。
- 失败、取消和断流不改变Draft或已确认状态。

### M6交付门

- 校验和节奏只提示，不替作者裁决。
- M6-02只读取已确认状态，pending StateProposal不参与权威校验。
- 全项目搜索覆盖Draft、只读Version和Entity，批量替换只作用于活动DraftBlock。
- 人工写作统计排除AI采用、导入、替换、恢复、结构和系统操作。
- DOCX复用既有导入协调器，三轨备份复用既有RecoveryService。
- 全项目替换、DOCX和备份恢复覆盖失败与恢复路径。

### M7体验门

- M7-01复用M5-00单一模式状态完成完整向导和三条路径。
- M7-02接入M6全部功能，但不重建基础导航、三栏布局或沉浸状态。
- 所有已实现功能有真实入口，StatusArbiter只反映真实Core状态。
- 两种视觉方向不分叉业务逻辑或状态源。
- 1280×800、2K、21:9和混合DPI可完成核心流程。

### M8发布门

- P0-001—P0-075全部Verified或明确Blocked。
- Skeleton、partial、state_extract、pending提案、GenerationRun引用和继续写作隐私硬门通过。
- 安全、数据、性能、E2E、AI Eval、人工写作统计和跨平台证据完整。
- README和用户文档只描述真实可用功能。

## 5. 并行规则

- M0-02与M0-03可在M0-01后并行，但M0-04必须等待两者。
- M1-08可与M1-03—M1-07部分并行，M1-09必须等待版本和恢复点。
- M5-00在M4阶段Verified后执行；M5-01必须等待M5-00和M4-05。
- M5-06必须等待M5-05和M3-06；M6-02必须等待M5-06。
- 同一阶段内仅依赖已满足且不修改同一权威契约的任务可并行。
- 不得并行修改同一Migration序列、IPC命令、Draft/Candidate/Version模型、Prompt版本或StateProposal来源合同。

## 6. V1.5启动门

V1.5不得按日期自动开始，必须满足：

1. V1.0已被真实作者稳定使用。
2. 已有中型或长篇项目数据。
3. FTS召回不足、失效传播成本或自动日记价值有可重复证据。
4. Core性能仍有余量或已达到明确拆分阈值。

V1.5包括L0—L5自动分层记忆、卷级检查点、定时项目日记、超长篇专项适配及有证据时的语义检索。
